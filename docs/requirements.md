# docs/requirements.md

## 1. 文書の目的

本書は、Python版RobotControllerが満たすべき機能要件、非機能要件、安全要件、互換性要件および受入条件を定義する。

詳細な通信形式は `docs/protocol-compatibility.md`、内部設計は `docs/architecture.md`、移行手順は `docs/migration-plan.md` に定める。

## 2. 背景

既存のRobotControllerは、VSTONE社の公式Java APIを利用し、Sota、CommUおよび設定名 `Dog` のロボットをTCP経由で制御するJavaサーバーである。

Python版では、既存クライアントとの正常系互換性を維持しながら、以下を改善する。

* Pythonによる保守性と教育上の扱いやすさ
* モック環境によるWindows上での開発
* 入力検証
* EOF、タイムアウト、過大入力への対応
* Pose、Motion、Idle Motionの排他制御
* 停止処理の確実性
* 音声一時ファイルとプロセス管理
* ロボット種別追加の容易さ
* ハードウェア依存部分の分離
* ログ、テスト、設定管理

## 3. 目標

### G-01 通信互換性

正常な既存クライアントが、接続先をJava版からPython版へ変更するだけで、既存の主要機能を利用できること。

### G-02 PC上での開発可能性

Windows上で、実機を使用せず、TCPサーバー、入力検証、コマンド処理、モーション制御、キャンセル処理をテストできること。

### G-03 実機動作

最終的に、Python版サーバーをロボット本体上で実行し、Javaを経由せずロボットを制御できること。

### G-04 複数機種対応

Sota、CommUおよびDogをサポートし、将来のロボットをプラグイン可能なバックエンドとして追加できること。

### G-05 安全性と堅牢性

不正な入力、通信切断、並行要求、停止要求、音声競合および初期化未完了状態を安全に処理できること。

## 4. 対象外

初期バージョンでは、以下を必須としない。

* 公開インターネットからの利用
* 高度なユーザー認証基盤
* TLS終端
* WebSocket、HTTP、REST、gRPCへの全面移行
* Java版の例外や不具合の再現
* 既存プロトコルv1へのACK追加
* 全ロボットの低レベルドライバの同時完成
* リアルタイムOS相当の厳密な時間保証
* 音声認識、音声合成、対話管理

## 5. 実行環境

### 5.1 開発環境

* Windows
* 必要に応じてWSL2
* Python仮想環境
* モックバックエンド
* pytest等のテスト環境

### 5.2 実機環境

* Edison版SotaのYocto OS
* CommUおよびDogの対応OS
* 各機種固有のデバイス、プロセス、音声再生環境

### 5.3 Pythonバージョン

実機Edison上の本番実行環境はCPython 3.6.15とする。本番コードはすべてCPython 3.6.15で構文解析・実行できなければならない。

以下を使用しない。

* Python 3.7以降で追加された構文および標準ライブラリAPI
* `from __future__ import annotations`
* `list[str]`、`dict[str, int]`等の組み込み型ジェネリクス
* `X | None`形式の型注釈
* 標準ライブラリの`dataclasses`
* `typing.Protocol`
* `asyncio.run()`
* Python 3.6で使用できないf-string構文
* Python 3.6で使用できない`pathlib`、`typing`、`asyncio`等のAPI

インタフェースには原則として`abc.ABC`を使用し、型注釈には`typing.List`、`typing.Dict`、`typing.Mapping`、`typing.Optional`等を使用する。開発ツールは新しいPython上で動作してよいが、本番コードをPython 3.6非互換の構文へ自動変換してはならない。

pytestはPython 3.6対応版を固定する。初期候補は`pytest==6.2.5`とする。

## 6. 機能要件

### FR-001 サーバー起動

サーバーは設定されたホストとポートでTCP接続を待ち受ける。

既定ポートは既存実装との互換性のため `22222` とする。ただし、設定で変更可能とする。

初期版はバックエンドの初期化が成功し、ライフサイクル状態が`ready`へ遷移してからTCP listenを開始する。

### FR-002 ロボット種別の選択

設定によって、少なくとも以下を選択できること。

* `Mock`
* `Sota`
* `CommU`
* `Dog`

未知のロボット種別は起動時エラーとする。

### FR-003 初期化状態

サーバーは次の状態を区別する。

* starting
* initializing
* ready
* degraded
* stopping
* stopped
* failed

ロボットが `ready` になる前に、ハードウェア操作を必要とするコマンドを実行しない。

初期版の正常な起動遷移は`starting` → `initializing` → `ready`とする。終了時は`stopping` → `stopped`、回復可能な機能低下は`degraded`、回復不能な初期化または実行失敗は`failed`で表す。

### FR-004 レガシープロトコルv1

`docs/protocol-compatibility.md`で定める既存プロトコルを実装する。

通信互換性とは、正常な既存クライアントが送るバイト列を受理し、同じコマンド効果を発生させ、v1では`read_axes`だけが応答を返すことをいう。処理タイミングの完全一致、JSONキー順序、JSON空白、不正入力時のJava固有挙動、Java版のクラッシュ・ハング・競合およびJavaの暗黙的な数値変換は互換性の対象外とする。

### FR-005 `play_pose`

単一のPoseを受信し、指定された遷移時間でサーボおよびLEDを制御する。

Poseには以下を含める。

* `Msec`
* 任意の `ServoMap`
* 任意の `LedMap`

`ServoMap`と`LedMap`の少なくとも一方を必要とする。

### FR-006 `stop_pose`

実行中の直接Poseを停止する。

停止完了後、停止前のキューに残ったPoseが自動的に再開してはならない。

停止動作の詳細は、ロボットバックエンドとスケジューラの安全方針に従う。

### FR-007 `play_motion`

Poseの配列を順番に再生する。

空配列、過大な配列、不正なPoseを拒否する。

### FR-008 `stop_motion`

モーションを安全かつ冪等に停止する。

モーション開始前、停止済み、完了済みの状態で呼ばれても例外を発生させない。

### FR-009 `play_idle_motion`

ロボット種別ごとに定義されたアイドルモーションを開始する。

入力として以下を受け付ける。

* `Speed`
* `Pause`

`Speed`は有限かつ正の数、`Pause`は0以上の整数とする。

### FR-010 `stop_idle_motion`

アイドルモーションを安全かつ冪等に停止する。

### FR-011 `play_wav`

WAVバイナリを受信し、ロボット側の音声出力で再生する。

サーバーは次を行う。

* 最大サイズの検証
* 最低限のWAVヘッダ検証
* 一意な一時ファイルの作成
* サーバー自身が起動した再生プロセスの追跡
* 再生終了後のファイル削除
* 新しい音声要求を受けた場合の方針に従った置換または拒否

### FR-012 `stop_wav`

サーバー自身が起動し、現在管理している音声再生だけを停止する。

`killall aplay`を使用しない。

### FR-013 `read_axes`

現在の軸角度を、ロボット種別ごとの軸名をキーとするJSONオブジェクトとして返す。

応答はv1フレーム形式で返す。

### FR-014 モックバックエンド

モックバックエンドは少なくとも以下を提供する。

* 現在軸角度の保持
* Pose適用
* LED値保持
* MotionおよびIdle Motionの検証
* 音声再生状態の模擬
* コマンド履歴
* 意図的な遅延または例外の注入

### FR-015 ロボットバックエンド

各ロボットバックエンドは、共通インタフェースを実装する。

最低限の機能は以下とする。

* initialize
* close
* read_axes
* apply_pose
* stop_motion
* play_audioまたはAudioManagerとの連携
* capabilities
* servoおよびLEDのプロファイル取得

### FR-016 将来機種の追加

新しい機種は、原則として以下の追加だけで対応できること。

* バックエンド
* 軸プロファイル
* LEDプロファイル
* 初期化設定
* アイドルモーション定義
* 実機テスト

TCPフレーム処理とコマンドルーターの変更を必須としない。

### FR-017 非公式実装の管理

非公式な低レベル実装を参照するときは、`docs/protocol-compatibility.md`のReference baselines節へ、リポジトリURL、検証済みの完全なcommit SHA、確認日、ライセンス、コピーしたコードか仕様だけを参考にした再実装か、および各レジスタ・ID・パケット・可動範囲の検証状態を記録する。

未確認の値を推測してはならない。完全なcommit SHAを確認できない場合はTODOとして残し、根拠を確認できるまで実機ドライバへ使用しない。

## 7. コマンド競合要件

### FR-020 単一の動作所有者

サーボ動作は、同時に1つの動作ソースだけが所有する。

動作ソースは以下とする。

* direct pose
* motion
* idle motion

### FR-021 優先順位

既定の優先順位を次のようにする。

1. 明示的な停止
2. direct pose
3. motion
4. idle motion

新しい上位優先度動作を受理した場合、下位動作をキャンセルする。

この規則は設定または将来仕様によって変更可能としてよいが、実行中に曖昧な混在を許可しない。

### FR-022 世代管理

各動作タスクに世代番号またはキャンセルトークンを付ける。

停止または置換された古い世代のタスクは、その後ハードウェアへ指令を送れない。

### FR-023 ハードウェア直列化

ネットワークスレッドはハードウェアを直接操作しない。すべてのハードウェアアクセスは、ネットワーク処理とは別の単一ワーカーを通して直列化する。

## 8. 入力検証要件

### FR-030 フレーム長

* ヘッダは4バイトbig-endianとする。
* 正常系v1で有効な長さは `0 <= length <= min(command-specific configured limit, 2147483647)` とする。
* `0x80000000`以上の値を拒否する。
* Frame Codecは長さ0を`b""`として処理し、必要な拒否はコマンド層で行う。
* Frame Codecは固定最大値を内部に持たず、呼び出し側から`max_length`を受け取る。
* ヘッダ不足、本文不足、EOFを明示的に処理する。

### FR-031 JSON

* UTF-8として厳密にデコードする。
* NaN、Infinity等の非標準数値を受理しない。
* トップレベル型を確認する。
* 未知フィールドの扱いを文書化する。
* 必須フィールドを検証する。

### FR-032 数値

* `bool`を整数として受理しない。
* 整数が必要なフィールドでは小数を暗黙に切り捨てない。
* すべての浮動小数点値について有限性を確認する。
* 範囲外値の丸めまたは拒否はフィールドごとに明示する。

### FR-033 サーボとLED

* 未知キーを拒否する。
* ロボット種別ごとの許可キーを使用する。
* 変換はロボットプロファイルに集約する。
* 変換結果が実機プロトコルの範囲内であることを確認する。

## 9. 非機能要件

### NFR-001 安全性

不正入力や通信異常によって、予期しない大角度、高速動作、無制限のキュー蓄積が発生しないこと。

### NFR-002 堅牢性

以下によってサーバープロセス全体が停止しないこと。

* 1接続の不正入力
* 途中切断
* 不正JSON
* 未知コマンド
* 開始前の停止要求
* バックエンドの一時的な例外

### NFR-003 リソース上限

設定可能な上限を設ける。初期既定値は次のとおりとする。

| 項目 | 初期既定値 |
| --- | ---: |
| command frame maximum | 64 bytes |
| JSON frame maximum | 1 MiB（1,048,576 bytes） |
| WAV frame maximum | 20 MiB（20,971,520 bytes） |
| maximum concurrent connection handlers | 16 |
| command and JSON read timeout | 5 seconds |
| WAV payload read timeout | 30 seconds |
| `read_axes` response write timeout | 5 seconds |

これらは絶対期限ではなく、各ブロッキングsocket操作に適用する無通信タイムアウトとする。段階終了時には、呼び出し前のsocket timeoutへ復元する。

* 同時接続数
* フレームサイズ
* WAVサイズ
* モーション要素数
* コマンド処理時間
* キュー長
* ログファイルサイズ

初期版のTCP接続処理は、同期ソケットと最大16ハンドラーの上限付き`ThreadPoolExecutor`を使用する。初期版では`asyncio`を採用しない。

### NFR-004 可搬性

ハードウェア非依存部分はWindows、LinuxおよびYocto環境で動作可能な設計とする。

### NFR-005 保守性

* モジュール間の依存方向を一方向にする。
* ロボット固有処理をバックエンドに閉じ込める。
* プロトコル仕様と実装を対応付ける。
* 型ヒントとテストを整備する。

### NFR-006 観測可能性

ログには少なくとも次を含める。

* 起動と終了
* 設定されたロボット種別
* 初期化結果
* 接続元
* 受信コマンド
* 入力検証エラー
* タスク開始、完了、キャンセル
* バックエンド例外
* 音声プロセスの開始と終了

サーボ値など詳細なデータをログへ出すかは、ログレベルで制御する。

### NFR-007 セキュリティ

初期運用は信頼された閉域ネットワークを前提とする。

最低限、以下を設定可能にする。

* bindアドレス
* 接続元IPの許可リスト
* 接続数制限
* 読み取りタイムアウト

外部ネットワークで使用する場合は、TLSまたは安全なトンネルを別途必要とする。

### NFR-008 テスト容易性

ネットワーク、時計、スケジューラ、バックエンド、音声プロセスをテスト時に差し替え可能にする。

本番コードのCPython 3.6.15構文互換性を継続的に検証し、pytestは初期候補`pytest==6.2.5`のようにPython 3.6対応版へ固定する。

## 10. 受入条件

### AC-001 プロトコル

`robo-tutorial`の既存クライアントから、以下が正常に利用できる。

* play_pose
* stop_pose
* play_motion
* stop_motion
* play_idle_motion
* stop_idle_motion
* play_wav
* stop_wav
* read_axes

### AC-002 不正フレーム

以下を送信しても、サーバーがクラッシュまたは無制限待機しない。

* 1～3バイトのヘッダ
* 過大な長さ
* 宣言長より短い本文
* 長さ0
* 不正UTF-8
* 不正JSON

### AC-003 動作排他

Motion実行中にdirect poseを送信した場合、定義された優先順位どおりに動作し、古いMotionが再開しない。

### AC-004 停止の冪等性

すべてのstop系コマンドは、対象処理が開始されていなくても安全に完了する。

### AC-005 モックテスト

Windows上で実機なしに主要機能の自動テストが完了する。

### AC-006 実機試験

ロボット種別ごとに、段階的な試験計画に合格する。

* 初期化
* 角度読み出し
* LED
* 単一軸
* 複数軸
* Pose
* Motion
* stop
* WAV
* Idle Motion
